# Self-hosted Temporal operations — optional fallback

The selected deployment is single-region Temporal Cloud with one worker VM per environment. Follow the [Cloud single-VM guide](../../ops/temporal/CLOUD.md). The database, replica, backup and restore requirements below apply only if the separate self-hosted fallback is explicitly selected; they are not prerequisites for Cloud staging or production.

## Status and ownership

The repository includes executable deployment, schema migration, backup, isolated recovery, certificate and worker release tooling. The optional self-hosted infrastructure described below has not been provisioned. The selected Cloud staging workers are deployed and verified with application dispatch disabled; application cutover and human smoke testing remain separate. Example self-hosted descriptors intentionally fail validation.

The optional self-hosted fallback topology uses two physically independent private clusters: staging and production each have at least three dedicated Kubernetes nodes, three independent PostgreSQL instances, and their own off-host backup identity/prefix. No components are added to the existing audio/Chrome VM. This separates CPU-intensive processing from the orchestration persistence layer and avoids turning a media-host restart into an application-wide outage.

Kubernetes adds operational work, but provides a concrete multi-node failover model for Temporal, PostgreSQL and side-by-side worker versions. A single Docker host cannot meet those availability requirements. Operators own OS patching, private API load balancers/VIPs, capacity, Kubernetes/CSI/CNI maintenance, object-store access, backup alerting, restore drills, certificate rotation and incident response. Nodes need SSD-backed durable volumes and enough spare capacity to sustain loss of one node while old workflow versions remain pinned. Size from summed rendered requests, measured peak memory/CPU, native media concurrency, retained worker builds and rollout surge; a generic three8-vCPU/16-GiB estimate is insufficient evidence for the complete application. The reviewed capacity plan must demonstrate scheduling and memory/storage headroom on the remaining nodes after one-node loss, then pass measured staging workload before production admission. Three nodes in one datacenter provide node failure tolerance, not datacenter resilience. Place replicas in distinct failure domains where the hosting network/storage support it, and keep backups outside the cluster's failure domain.

All application admission travels through the Firestore outbox. Firebase clients and the browser never connect to Temporal. Domain workers poll private task queues. Media, email, image and search activities have separate worker deployments/concurrency and scoped runtime secrets. Their `TEMPORAL_DEPLOYMENT_NAME` and build ID remain common so one Temporal deployment version includes all required queues.

## Release and deployment inputs

`ops/temporal/versions.json` pins the official Helm chart/checksum, server/admin/UI/PostgreSQL image digests, CloudNativePG and Barman manifest checksums. The K3s recipe uses 1.36.5, the newest supported Kubernetes minor for CloudNativePG 1.30; 1.37 is tested but not officially supported. The PostgreSQL operand is 18.6, Temporal 1.32.1, CLI 1.9.1, UI 2.55.0, CloudNativePG 1.30.1 and Barman plugin 0.15.1. Recheck compatibility and release notes when updating this contract.

Copy both environment descriptors outside the repository. Required fields include a concrete Kubernetes context and immutable `kube-system` namespace UID, separate private API and database identities, explicit provider HTTPS egress CIDRs, persistent storage class, off-host backup endpoint/prefix, immutable worker image digest/full commit, enabled domain roles, and a recent restore-evidence file. Temporal namespaces equal the Firebase projects: `urm-app-staging` / `urm-app`. The renderer checks peer descriptors to reject shared cluster identities or database/backup endpoints.

`databaseMode: self-hosted` deploys the complete CloudNativePG recipe; `existing-ha` connects to an operator-supplied HA PostgreSQL service with independently verified PITR. The latter still requires both databases, trusted TLS, credentials and restore evidence. Kubernetes contexts are always explicit; commands do not depend on the user's current context.

```sh
node scripts/temporal-platform.mjs validate --config /secure/staging.json --peer /secure/production.json
node scripts/temporal-platform.mjs render --config /secure/staging.json --peer /secure/production.json --output /tmp/temporal-review
node --test scripts/temporal-platform.test.mjs
HELM_BIN=helm PYTHON_BIN=/path/to/validator/python node scripts/validate-temporal-manifests.mjs
```

The final command needs PyYAML 6.0.3 and jsonschema 4.25.1 in a QA-only Python environment; it validates actual chart rendering and CNPG/Barman objects against pinned official CRDs. It does not connect to any cluster.

## Dedicated private host recipe

For self-hosted Kubernetes, fill a distinct `ops/temporal/nodes.example.json` inventory for each environment. Three or more odd-numbered server nodes use embedded etcd quorum; a separate private HA API VIP/load balancer routes6443 to healthy servers. Do not point the VIP at only one node. Provision the nodes/storage/network only after the hosting budget is agreed.

```sh
node scripts/temporal-k3s-config.mjs --inventory /secure/staging-nodes.json --peer-inventory /secure/production-nodes.json --output /secure/staging-k3s
```

The generator emits per-host config and a version-pinned, checksum-verified installation script. On the reviewed dedicated Ubuntu hosts, install each JSON config as `/etc/rancher/k3s/config.yaml` (JSON is valid YAML), and securely distribute a single environment-specific random cluster token to `/etc/rancher/k3s/cluster-token`, both mode 0600. Start the first node before the joining nodes; run the emitted script on each host. It does not run SSH or create servers automatically.

Before installation, configure the OS kernel/kubelet prerequisites for `protect-kernel-defaults`, WireGuard kernel support, time synchronization, disabled swap, and a supported persistent CSI driver. The private interface must carry all node traffic. Permit 6443 only from nodes/operator VPN,2379–2380 only between control-plane nodes, 10250 only between trusted cluster nodes/control-plane, and UDP 51820 only between nodes for encrypted pod traffic. Do not expose Kubernetes, etcd, PostgreSQL, Temporal 7233, metrics or UI 8080 publicly. SSH is restricted to the operator network. Do not disable K3s network-policy enforcement; test real default-deny ingress/egress probes before enabling application admission.

Use independent node disks/volumes and required anti-affinity for the three PostgreSQL copies. The local-path development provisioner is unsuitable for the production storage contract; choose a durable CSI storage class with documented host-loss/replacement behavior and tested restore. K3s snapshots run every six hours; create the `temporal-etcd-backups` S3 configuration Secret in `kube-system` with a separate off-host prefix and least-privilege identity. Back up the cluster token offline alongside the etcd snapshots; the token is required to decrypt bootstrap data during recovery. A PostgreSQL backup is not an etcd/configuration backup.

Create the target namespace with restricted Pod Security enforcement first. Install cert-manager 1.21.2 from its official versioned manifest before the operators. Use SHA-verification/signature verification for downloaded infrastructure artifacts. The database operator installer verifies repository-pinned CNPG/Barman manifests and waits for controller rollouts. CloudNativePG installs in `cnpg-system`; the Barman plugin must be in the same namespace.

```sh
node scripts/deploy-temporal-platform.mjs cert-manager --config /secure/staging.json --peer /secure/production.json --apply
node scripts/deploy-temporal-platform.mjs operators --config /secure/staging.json --peer /secure/production.json --apply
```

Create the target namespace before running platform operations, with restricted Pod Security enforcement. The deploy tool verifies cluster UID and at least three Ready schedulable nodes before any mutation. It serializes operations with `temporal-platform-operation-lock`; a crashed operation leaves a visible lock. Remove a stale lock only after confirming that no operation/jobs or CI runner are still active. Never run direct routing changes concurrently with this tooling.

## Secrets and private TLS

Secrets must be independently provisioned in each cluster; no real credentials are stored in descriptors/rendered files:

| Secret                           | Required fields and purpose                                                                                     |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `temporal-root-ca`               | `tls.crt`, `tls.key`; private CA issuer, managed through the operator's secure PKI                              |
| `temporal-database`              | `username: temporal`, `password`; non-superuser owner of both databases                                         |
| `temporal-backup-objectstore`    | `ACCESS_KEY_ID`, `ACCESS_SECRET_KEY`; dedicated backup writer restricted to the environment prefix              |
| `temporal-firebase-<role>`       | `service-account.json`; separate least-privilege Firebase identity for each role in the matching project        |
| `temporal-worker-<role>-runtime` | Domain-specific provider configuration/credentials; separate for orchestration, media, email, images and search |
| `temporal-search-config`         | `instances.json`; private search instance configuration/write keys, only mounted in search workers              |

The `certificates` operation creates rotating 90-day mTLS certificates for internode, frontend, worker, operator, UI and database server identities, and publishes the public database trust CA. Store the private root CA key outside the cluster in the PKI backup as well. Server/DB certificate SANs must match the reviewed private identities. Runtime connections override the service-DNS server name using `TEMPORAL_TLS_SERVER_NAME`; host verification remains enabled. Temporal refreshes mounted certificates every minute; workers detect rotated TLS file contents and drain/restart automatically using the same immutable version. Frontend and internode require client certificates. Internal frontend authorization bypass is disabled; PostgreSQL requires verified TLS; all exposed services are ClusterIP with no ingress.

```sh
node scripts/deploy-temporal-platform.mjs certificates --config /secure/staging.json --peer /secure/production.json --apply
node scripts/deploy-temporal-platform.mjs database --config /secure/staging.json --peer /secure/production.json --apply
```

mTLS identifies trusted cluster clients; it does not provide namespace authorization by itself. Physical environment isolation and narrowly scoped certificate/RBAC distribution are the trust boundary. Do not share worker/operator credentials or introduce unrelated tenants into either cluster. If that trust model changes, add an explicit JWT ClaimMapper/Authorizer before doing so. Never make the mTLS frontend public.

Email workers receive the existing kit configuration (`SMTP_CONNECTION_URI`, `SMTP_PASSWORD`, `DEFAULT_FROM`, `MAIL_COLLECTION`, `TLS_OPTIONS`, template/user collections, TTL and optional OAuth settings) from the email-only runtime Secret. Media workers receive their scoped Firebase bucket/database and media runtime settings. Search workers receive `TEMPORAL_SEARCH_CONFIG_FILE=/run/search/instances.json`; staging omits search until a valid staging Algolia application is supplied. The worker image defines its prebuilt workflow bundle path. SDK credentials and provider secrets are resolved in activities, never in workflow history inputs.

## Persistence migrations and server rollout

CloudNativePG initializes the `temporal` owner/database and declaratively creates `temporal_visibility`. It requires one synchronous standby acknowledgment for commits; if both standbys are lost, writes stop rather than silently weakening durability. PostgreSQL max connections are sized for current replica counts; recalculate total SQL pools before scaling Temporal.

First take a completed physical backup of the current fresh CNPG cluster. `schema-bootstrap` is a distinct operator action: it verifies the current physical PostgreSQL identity/primary, a recent backup created after that cluster, zero public application tables in both databases, and no existing Temporal pods. It initializes both schema versions without accepting an empty restore as application readiness proof. After bootstrap, take a new backup and prove an isolated restore with actual Temporal schema/PITR markers before running server/worker admission gates. This ordering avoids requiring schema markers before the initial schema exists. External managed HA PostgreSQL requires its provider-reviewed guarded initial setup; this automatic empty-schema bootstrap applies only to the complete self-hosted CNPG recipe. It is never run during normal upgrades. Schema jobs have zero automatic retries so partial migrations remain visible. After any failed migration, inspect the version table/release-specific migration behavior before retrying.

```sh
node scripts/deploy-temporal-platform.mjs schema-bootstrap --config /secure/staging.json --peer /secure/production.json --apply
node scripts/deploy-temporal-platform.mjs server --config /secure/staging.json --peer /secure/production.json --apply
```

`server` performs explicit `temporal-sql-tool` updates for both databases, then installs/upgrades the checksum-pinned chart, waits for distributed replicas, and performs a real mTLS namespace operation. SQL schema changes precede server changes. Never automatically Helm-rollback database schemas. Server upgrades cannot skip minor versions or downgrade; advance through each latest patch/minor and allow at least ten minutes per minor for shard metadata processing, as documented by Temporal. `historyShards` is immutable after initialization: changing it requires a new cluster and migration. Scale replica counts without changing the shard count.

## Immutable worker releases, ramping and rollback

The worker Docker image must be built/tested by CI and referenced by digest; `workerBuildId` is its full source commit. Update the reviewed descriptor for the candidate version. Each enabled domain gets its own immutable Deployment and scoped Secret, two replicas, default-deny policy, readiness checks and a 180-second shutdown budget. Old versions stay running. All queues of one release share the same deployment version. `/readyz` verifies connected pollers and dispatcher readiness rather than merely an open TCP port.

```sh
node scripts/deploy-temporal-platform.mjs worker --config /secure/staging.json --peer /secure/production.json --apply
node scripts/deploy-temporal-platform.mjs ramp --config /secure/staging.json --peer /secure/production.json --percentage 10 --apply
node scripts/deploy-temporal-platform.mjs promote --config /secure/staging.json --peer /secure/production.json --apply
```

No `allow-no-pollers` or `ignore-missing-task-queues` override is used. A candidate missing a required queue cannot become current. Start first-ever versions with `promote`; established deployments can ramp 10%, then 50%, then promote after smoke checks/latency/error observation. Production requires the separately reviewed promotion after staging smoke tests. Rollback means `promote` with the previous version's descriptor; pinned executions already started on the candidate continue there until completion unless an explicit recovery procedure moves them.

Do not delete old pods based on elapsed time or zero CPU. The `retire` operation obtains a live Temporal deployment-version report and requires the exact build to be DRAINED and neither current nor ramping, under the same operation lock. Keep each old release descriptor until its version is retired. Long-lived pinned workflows use Continue-as-New upgrade boundaries; an auto-upgrade workflow requires replay-safe patching. Never mutate an image under an existing build ID.

## Continuous backups and isolated point-in-time recovery

The Barman plugin continuously archives WAL, with `archive_timeout=60s`, and takes an immediate plus nightly base backup. Both databases are in the same PostgreSQL physical backup. Archive latency and failed backups must alert; 60 seconds is a requested WAL segment switch interval, not a guaranteed RPO. Object-store failure or archive lag increases data-loss exposure. Enforce at-rest encryption, versioning/object lock where supported, a 30-day retention policy and an independently secured off-host account. Test that cleanup cannot remove the last recoverable chain. Off-host prefixes/identities cannot be shared between environments.

```sh
node scripts/temporal-backup.mjs backup --config /secure/staging.json --peer /secure/production.json --apply
node scripts/temporal-restore-witness.mjs prepare --config /secure/staging.json --peer /secure/production.json --output /secure/witness.json --apply
node scripts/temporal-backup.mjs render-restore --config /secure/staging.json --peer /secure/production.json --restore-namespace temporal-restore-drill --witness /secure/witness.json --output /secure/restore.json
```

Before applying a restore manifest, provision its namespace's read-only `temporal-restore-objectstore` credentials, public database CA and database-server certificate. The rendered restore creates a distinct CNPG cluster, reads the original backup server prefix, restores to an explicit past time, has no archiver writing to the source prefix, and includes no application worker or Temporal server. Default-deny networking blocks unrelated clients. It never overwrites live database objects. The witness preparation explicitly writes two UUID probe markers in a PUBLIC-revoked operations-only schema in both databases, takes/waits for a full physical backup, chooses the PostgreSQL server target time, commits later markers and confirms WAL archival. It does not modify Temporal application tables. Render derives the exact target from the private witness file; an optional explicit target must match. This creates a provable recovery boundary even before Temporal server starts.

```sh
kubectl --context PRIVATE_CONTEXT apply -f /secure/restore.json
node scripts/temporal-backup.mjs verify-restore --config /secure/staging.json --peer /secure/production.json --restore-namespace temporal-restore-drill --witness /secure/witness.json --output /secure/staging-restore-report.json
```

Verification requires the exact Temporal persistence/visibility tables and pinned schema_version markers, PostgreSQL system identifier matching the current source cluster, matching archive endpoint/prefix and a completed pre-target source backup. It requires each restored database contain the before-target witness and exclude the after-target witness, with matching source/backup identities. It also checks PostgreSQL JSON recovery logs prove the requested time boundary was reached; Ready/readable empty databases are rejected. Collect and verify the drill immediately before recovery logs rotate or the initial restored primary changes; missing boundary proof fails closed. Deployment gates reject older generic restore evidence and compare its PostgreSQL physical identity with the current live cluster. The deploy gate requires successful backup evidence under 48 hours old and an isolated restore drill under 30 days old. For a real incident, also validate schema/history integrity and the chosen recovery boundary, measure achieved RPO/RTO, reconcile provider side effects since that boundary, and get the operator's reviewed traffic-switch plan before connecting any workers. Restoring Temporal can replay activities whose external effects occurred after the restored timestamp; provider idempotency/reconciliation is mandatory. Do not automatically switch to the recovery cluster.

## Media scratch capacity

A media pod accepts20GiB sources and bounds each encoded output to20GiB. Native activities reserve64GiB total workspace plus16GiB free-disk headroom before acquisition; the platform explicitly sets the matching byte-limit environment variables. The helper checks source bytes during streaming, caps native outputs/workspace while processes run, and aborts/drains child processes on a bound breach. A compressed source size alone cannot predict decoded/encoded output size. Platform validation requires source + two outputs + bumper allowance, then `concurrency * workspace + headroom`; concurrency2 therefore needs at least144GiB usable scratch. The examples allocate160GiB per media pod, with CPU2/memory2Gi requests and4Gi memory limit. Increase these limits only alongside admission/runtime byte budgets and measured concurrency; never raise concurrency alone.

Each media pod gets its own generic ephemeral RWO CSI volume mounted at `/tmp`, with UID/GID/fsGroup1000 and no hostPath. Scratch is disposable after pod loss; immutable acquired sources/artifact checkpoints must remain in durable application Storage for safe retries. The media storage class must provide hard capacity isolation, topology-aware binding, `WaitForFirstConsumer`, `Delete` reclaim and filesystem support for requested ownership. Local-path/hostPath provisioners are rejected at deployment. The separate media class profile permits a class-scoped namespace storage quota: the example960Gi budget covers two retained builds, two replicas and one surge pod per build. Quota prevents unbounded allocation; it does not create physical capacity. Provision enough CSI backing/node space and failure-domain capacity for all live old versions, surge and one-node failure before enabling admission. Workflow versions may remain pinned longer than two releases; increase reviewed quota/backing capacity rather than deleting undrained workers.

Alert on PVC byte/inode exhaustion, CSI quota pressure and pod scheduling/provisioning failures. Integrate kube-state-metrics resource-quota discovery and authenticated kubelet volume metrics; verify alerts against the actual CSI filesystem and provisioner. A disk preflight/reservation failure must leave the durable request retryable, not accepted as successfully processed. Monitoring and storage provisioning are deployment acceptance gates, not claims established by static rendering.

## Private API and email connectivity

`kubernetesApiEndpoints` explicitly lists the private Kubernetes Service address on443 and each private API node/VIP endpoint on6443 as /32 addresses. Account for the CNI's pre/post-DNAT policy behavior; deployment compares the list with actual Kubernetes Service/Endpoints and refuses drift. Never add a public0.0.0.0/0 API rule. PostgreSQL primary and isolated restore instances inherit the same explicit network profile. Before database/server acceptance, a read-only Node canary uses the generated CNPG service account, mounted CA/token and that identical network selector to verify certificate hostname, authenticated access and the UID of an existing PostgreSQL pod through every reviewed API endpoint. No credentials or API response body are logged. CNPG instance-manager API access is required for status/configuration/certificate reconciliation.

Orchestration workers alone receive a projected short-lived Kubernetes token and downward pod/node identity. Their namespace Role permits Pod GET; dynamic Pod names prevent static resourceName scoping, so no list/watch/Secret reads are granted. The cluster Role permits Node GET only for `workerIdentityNodeNames` and namespace GET only for `kube-system`, whose UID is the actual cluster identity. Nodes added to the cluster require a reviewed allowlist update. Other domain workers receive no Kubernetes token. Unknown account executions use the separate [account execution recovery procedure](ACCOUNT_EXECUTION_RECOVERY.md) and audited `scripts/temporal-reconcile-account-execution.mjs`; preserve originating pod/node/container identity evidence. TTL or a deleted Pod alone cannot prove a partitioned worker stopped. The audited script proves termination using the actual private Kubernetes API and node-proxy evidence, records only the private execution fence, and never writes Auth claims, resumes work or marks an account change applied. Private API egress is scoped to orchestration and CNPG profiles; provider and database traffic remain separate.

`emailEgress` is a reviewed nonsecret provider descriptor mounted at `/run/email/egress.json`: schemaVersion1, provider (`smtp` or `sendgrid`), hostname, port, TLS mode, literal addresses. SMTP supports465 implicitTLS or587 requiredSTARTTLS; its extra network policy grants only those exact /32 or /128 addresses and port to email-role pods. SendGrid uses actual `api.sendgrid.com:443` transport. OAuth SMTP additionally requires `oauthTokenEgress` with the canonical Google token hostname,443 and reviewed literal addresses. Runtime secrets hold credentials independently. Provider code rejects insecure TLS and endpoint mismatches, checks DNS answers against the reviewed address set and preserves certificate hostname validation when pinning a connection address. DNS drift fails closed: update the reviewed descriptor/network allowlist and rerun verification through the protected deployment workflow, or use a privately managed stable egress relay with the same TLS guarantees. Do not widen internet SMTP access to restore service.

Each release live-worker check runs a private provider-aware canary from the actual email network profile and immutable image using the email runtime secret. SMTP verification checks TLS/authentication without SMTP DATA and reports mailPermissionVerified false: it cannot prove sender/recipient acceptance or delivery without a real send. Those properties belong in normal open-staging E2E coverage. OAuth binds and verifies the actual credentials. SendGrid uses read-only authenticated GET/v3/scopes and requires mail.send. No envelope/mail body is generated and no mail-send endpoint is called. A missing/bad TLS/auth proof blocks ownership transfer and admission opening. Temporary DNS/provider outages leave durable requests pending for recovery rather than bypassing the canary.

## Deterministic application cutover

App Hosting normally rolls `main` or `staging` independently of Functions deployment. A new durable-only UI cannot safely be merged while ownership flags still point to legacy handlers. Conversely, transferring ownership while old browsers can write legacy canonical documents creates lost or duplicate work. Use the explicit checkpoint controller; it never silently submits Cloud Tasks when Temporal admission is unavailable.

Before merging the new UI commit, copy `ops/temporal/release.example.json` to a private reviewed descriptor, fill the immutable backend/UI commit IDs, release UUID, exact environment and evidence paths. Keep this descriptor unchanged for the release. `initial-cutover` requires legacy ownership; future releases use `durable-upgrade`. Stage deliberately excludes search until its replacement Algolia credentials are ready. Production includes search. Run `node scripts/temporal-release.mjs plan --release /secure/release.json` for an offline plan. Every live operation below additionally requires `--apply`. No operation in this change has been run against a remote application.

1. Run `freeze-ui` **before** pushing a branch that would automatically roll. It saves known-good UI traffic and the current automatic rollout policy, atomically pauses application admission, and disables only `rollout_policy.disabled` through the official App Hosting API with an etag and request UUID. Firebase CLI has no automatic-rollout-policy mutation command. An active rollout or inconsistent live branch blocks freezing. The existing production `main` backend wiring is preserved.
2. Deploy the reviewed compatibility backend, all extension kits, and Firestore rules while ownership remains legacy. This deployment must include atomic `legacyAdmissionLeases`, private release-control admission checks, and old-browser write fencing in every ingress. Existing work/continuations may finish. Record and test those properties in the compatibility evidence, then run `compatibility-ready`. The controller waits at least the maximum execution timeout observed **before and after** deploying compatibility handlers, with an explicit reviewed grace of at least3600 seconds covering the existing3570-second native HTTP timeout, so old unfenced invocations can finish before drain proof. A zero-traffic Cloud Run revision does not establish that background work has terminated. Unresolved legacy email PROCESSING records, including expired leases, remain drain blockers until the originating runtime is confirmed terminated and provider effects are audited; changing a record to ERROR merely to obtain a green drain result is not a valid reconciliation.
3. Run `drain`. It discovers project task queues and requires empty task lists, zero active audio request/lock/mutation-claim/deferred-auth/probe state, zero unresolved publishing locks, no unfinished legacy mail, and no active or uncertain admission lease across any domain. Expired leases and locks still block. Finish or explicitly reconcile deferred authentication jobs; do not delete them to obtain a clean count. No dispatcher or old worker version is retired by this step.
4. After drain, run `provider-usage-ready`. For initial cutover it emits a fresh revision-fenced drain proof and invokes `temporal-backfill-provider-usage.mjs` to establish the private canonical provider-reference index while media/publishing/images/accounts remain legacy and paused. Existing ambiguous delete reservations are never expired into permission to delete. The controller verifies the ready project/schema/epoch, records it in the checkpoint, and checks it again in the ownership-transfer transaction and before opening. Readiness requires every current backfill source group, including `temporalProviderAcknowledgementReviews` and `temporalProviderRetentions`; earlier nine-group proofs cannot authorize cutover because they omit reviewed permanent resource edges and deletion tombstones. Later durable upgrades verify the existing ready epoch instead of rescanning around live Temporal continuations. Backfill stores its original revision; later control transitions do not falsely invalidate it. Interrupted backfills resume the same building epoch from a durable100-document page cursor; partially completed pages safely replay idempotent edges, and ready is written only after all groups complete. Configure `providerUsageBackfillTimeoutMs` for the reviewed maintenance window (one minute through24 hours, default30 minutes); the runner/workflow deadline must also accommodate it. Timeout leaves admission paused and the checkpoint resumable.
5. Deploy the private platform and immutable workers using the platform controller. Register/promote the reviewed build through Temporal's native deployment-version CLI. Operator jobs use the separately pinned official CLI1.9.1 image, while SQL jobs use Server-matched admin-tools. Readiness/retirement parsers follow the CLI's actual formatted JSON (typed activity/workflow queues, routing fields and null-timestamp representation), rather than assuming raw gRPC shape. Run `workers-ready`: it checks physical-cluster identity, restore evidence, actual pod readiness and live Temporal routing/queue registration. Selected domains require their full queue-role mapping: media→media, images→images, emails→email, search→search; publishing/accounts/bundles→orchestration, with orchestration and the separate lifecycle controls queue always present. Controls workers have10 activity slots (`TEMPORAL_CONTROLS_CONCURRENCY`), no dispatcher, no provider mutation secrets, and scoped Firebase Auth getUser/Firestore lifecycle/GCS metadata and revision-owned RTDB progress-cleanup permissions. They cannot be starved by media or publishing-provider activity slots. The worker build must equal the immutable reviewed compatibility commit. Build images with required `--build-arg TEMPORAL_IMAGE_BUILD_ID=FULL_SHA`; production startup verifies the root-owned `/etc/temporal-worker-build-id` marker matches the deployment build ID. Environment variables cannot replace the baked marker. Record/pin the resulting digest and verify registry provenance/OCI revision against the reviewed commit before deployment. Declare `imagePullSecrets` explicitly; private GHCR/Artifact Registry images need preprovisioned namespace-scoped dockerconfigjson credentials. A reviewed empty array is allowed only for public or deliberately preloaded images. The worker deployment verifies named Secret types/fields and propagates pull credentials to worker-image TLS/SMTP/API canary jobs, including any isolated namespace where those canaries are used. Registry credentials are separate from application Firebase/provider credentials and are never printed. All selected queues must have pollers and the build must be current with no ramp in progress. These live checks repeat immediately before ownership transfer and opening admission.
6. Run `take-ownership`. It repeats legacy drain checks and checks unresolved leases in the same Firestore transaction that changes selected owners to Temporal. Admission remains paused. This transaction conflicts with a concurrent legacy lease acquisition, closing the read-before-provider-effect race.
7. Materialize supported Functions `.env.<project>` files from the private control document, then deploy **all** Functions codebases, extension kits and runtime services from the reviewed compatibility commit. Run `backend-ready`. It verifies actual deployed Functions ownership flags and `TEMPORAL_RELEASE_COMMIT`, plus fresh deployment evidence for the independent native/runtime services and facade behavior. Shell environment variables alone are insufficient.
8. If bundles are selected, run `bootstrap-bundles`. It submits six deterministic release intents and awaits current-generation successful immutable artifact pointers while admission remains paused. A superseding successful generation counts; a stale or merely queued bootstrap does not. Failed convergence leaves the release paused.
9. Run `rollout-ui`. It first persists deterministic named build/rollout IDs and request UUIDs derived from release/project/commit. The official CLI was evaluated first, but cannot expose caller-selected identities needed to recover a crash before acceptance. This step therefore uses the official named Build/Rollout REST create APIs. On retry it reads those exact resources, recreates an absent resource with the same immutable identity, reconciles uncertain acceptance, and blocks conflicting active rollouts. Once settled it verifies the exact READY build and successful rollout serve100% of traffic. Timeouts remain paused and resumable; a failed artifact requires a reviewed recovery release. Existing pre-identity CLI checkpoints are rejected for separate read-only reconciliation.
10. Before opening, perform **readonly and existing-admitted-job** smoke only: UI/identity/role loading, old-browser write rejection, backend ownership, actual worker/poller connectivity and completed permitted bundle continuations. Fresh upload/provider/account writes correctly fail while global admission is paused. Label this evidence `scope: "preopen-readonly-and-existing-jobs"`, `readonlySmokePassed: true`; it must not claim fresh-write E2E. Run `open` after these gates to atomically open selected Temporal admission. On staging, then perform real uploads/provider/email/account flows and failure injection through normal admission while open, followed by the user's full smoke test. Production promotion requires that acceptance; seeded frontend rendering cannot replace it. Production pre-open evidence has the same limited scope, and real production writes occur after normal opening. Run `restore-auto` after opening to restore the saved disabled flag on the original live-branch policy. Automatic rollout is never restored on a failure path.

Before production `freeze-ui` (and any main push/promotion), supply `promotionApprovalEvidence` from the reviewed staging test run and actual human acceptance. It must identify schemaVersion1, `scope: "open-staging-end-to-end"`, stageProjectId `urm-app-staging`, actual stage backend/UI commit IDs, approved target backend/UI commit IDs, result passed, verifiedAt within seven days, failureInjectionPassed/userSmokePassed true, and testedDomains. `humanApproval` contains approved true, actual reviewer identity, approval timestamp after the smoke result, source `protected-environment-review` or `explicit-user-message`, and an immutable evidence reference. This is a trusted operator/CI artifact of real results and authorization, never a fabricated placeholder. Every selected production domain needs actual staging coverage; search alone can have a separately human-approved `untestedDomainWaivers` entry with a substantive reason when replacement staging Algolia is unavailable. Neither seeded UI tests nor a generic admission bypass qualify. The controller checks scope/commit/domain/approval binding before production freeze; protected production environment reviewers remain the approval authority.

All checkpoint actions use private Firestore control state, a nonexpiring operator lock, expected revisions and immutable descriptor identity. A crashed operator lock requires audited inspection before manual reconciliation; expiry is not proof that the operation finished. `temporal-release.yml` exposes each checkpoint separately on the protected private runner and shares the platform operation concurrency group. Configure `TEMPORAL_RELEASE_CONFIG_JSON`; referenced platform descriptors/evidence must already exist at their reviewed private runner paths. The runner needs separate narrowly scoped ADC and CLI identities for Firestore/RTDB, App Hosting policy/rollout, Functions configuration, Cloud Tasks read-only enumeration and private Kubernetes/Temporal operations. Keep output/checkpoints private: configuration contains operational topology, never provider secrets.

Every subsequent Functions and kit deployment must regenerate ownership files **after** environment/config generation and kit copying, before either deploy:

```sh
node scripts/temporal-function-env.mjs --project "$FIREBASE_PROJECT" --from-control --apply
```

The generator preserves other settings, fails closed on missing/invalid control, sets every `TASK_ORCHESTRATOR_<DOMAIN>` from source control and records the actual immutable commit. In CI `GITHUB_SHA` supplies that commit; operators can pass `--commit FULL_SHA`. App Hosting secrets are not Functions environment settings. Native Hetzner/Cloud Run services require their own reviewed runtime configuration deployment and evidence.

Compatibility and backend evidence files are fresh JSON reports (under one hour old) with `projectId`, `releaseId`, `controlRevision`, `result: "passed"`, `verifiedAt`, and `commit`. Compatibility requires `legacyAdmissionPauseVerified`, `legacyAdmissionLeaseFencingVerified`, `oldBrowserWritePauseVerified`, `allSourcesDeployed` true. Backend requires `allSourcesDeployed`, `runtimeServicesDeployed`, `facadeOwnershipVerified` true. Smoke evidence requires `uiCommit`, `backendOwnershipVerified`, `workerReady`, `oldBrowserWritesDenied` true. These are actual operator/test-runner results, not generated optimistic placeholders; the controller also independently verifies live service state.

Uncertain/crashed legacy leases require an independently verified provider/canonical outcome and confirmed stopped runtime. `scripts/temporal-reconcile-legacy-lease.mjs --review /secure/review.json --apply` verifies the **same ADC** IAM actor through Google's token-introspection endpoint, fences every observed lease field in a transaction, requires both global/domain admission paused, rejects recently heartbeating active leases, and creates an immutable `legacyAdmissionLeaseReviews` audit before completing the lease. Review JSON includes projectId, leaseId, review UUID, decision (`completed_no_effects` or `completed_verified_effects`), substantive reason, immutable HTTPS/gs evidence references, fresh verifiedAt, runtimeEndedVerified/providerEffectsVerified true and observed state/acquiredAt/effectsStarted/releaseRevision/heartbeatAt/diagnosticExpiresAt. A diagnostic expiry alone never permits completion. This operation does not retry a provider effect; tightly restrict its operator IAM access. ADC without a verifiable email identity fails closed.

For recovery, run `pause` first; existing workflow jobs and pinned workers remain. `rollback-ui` may restore the saved UI build while admissions stay paused and owners stay Temporal. It does not make old mutating UI actions compatible. Repair/redeploy the same reviewed artifacts. After a UI rollback, run `restore-reviewed-ui`: it verifies the stored immutable build/commit, restores100% target traffic, reapplies the frozen branch policy (traffic target/policy are a union), and returns to ui-ready without changing owners/admission. Rerun fresh readonly smoke and open. For other failures rerun the failed checkpoint; `resume` restores the saved pre-pause phase and requires the reviewed live UI when resuming a previously opened release. Then rerun smoke evidence and `open`; never rewrite ownership to legacy while Temporal executions or uncertain external effects remain. A changed code artifact requires a separately reviewed recovery procedure and new descriptor/checkpoint migration, rather than silently editing an in-flight release. Retain previous worker versions until Temporal reports them DRAINED.

## Recover a failed first staging compatibility deployment

`temporal-recover-initial-compatibility.mjs` is a separately reviewed recovery procedure for one specific boundary: staging initial cutover still at `ui-frozen`, every domain owned by legacy and paused, and no compatibility cutoff or completed compatibility gate. It does not support production, later stages, admission reopening, owner rollback or shortening any grace. Do not edit the failed release descriptor's commit pins to retry different code.

1. Settle the failed deployment's actual Functions, Cloud Build and Cloud Run operations and inspect the failed runtime. Preserve the original guard identity and settlement artifacts; explicitly reconcile its retained lock only after confirming all asynchronous work has settled. Recovery never steals or expires that lock. Preserve the original old descriptor, old UI traffic and original browser actor identity proof.
2. Review and commit the corrected source. Wait for the exact candidate commit's `Temporal application validation` workflow to finish successfully. Create a new descriptor with a new release UUID, identical staging scope/queues/domains, nondecreasing grace/maintenance limits, new evidence paths and backend/UI commits equal to the exact new checkout. Worker readiness for the new candidate is a separate later gate; this command does not certify or enable dispatch.
3. Prepare a fresh reviewed JSON file with schemaVersion1, projectId, oldReleaseId, newReleaseId, oldControlRevision, verifiedAt (within ten minutes), candidateCiRunId, a substantive reason, originalOperatorUid, and operatorIdentity containing the same actorUid/authTime plus fresh verifiedAt. Include settledGuard with original operationId/action `controlled-backend-deploy`/releaseId/commit/createdAt, and guardSettlementVerified/failedCompatibilityDeploymentVerified true **only after actual inspection**. The original identity artifact must predate the original freeze; the current account is independently checked as enabled/admin and its authTime checked against revocation. That browser identity is recorded as reviewedBrowserActorUid; it is not attribution of the ADC principal (`claimsADCActorIdentity:false`). No token export is needed.
4. Include `operations` records `{apiVersion:'v1'|'v2',name,done:true}` for actual old deployment operations; at least one independently reread operation must have an actual error and creation time after the failed guard started. Include `builds` records `{name,status}` for reviewed terminal builds and `runtime` records `{name,state,build,revision}` matching actual current Functions projections (`buildConfig.build`/`serviceConfig.revision`, or null). CamelCase function names are supported. Include `artifacts` records `{label,path,sha256}` for immutable local runtime/settlement evidence; the required `original-operator-identity` label identifies the original top-level identity JSON. Hashes here cover the exact file bytes; descriptor/review hashes in the resulting archive use canonical JSON. These are factual operator evidence, not manufactured defaults.
5. Run the read-only command from that exact clean candidate checkout using Node22. Both dry run and apply require a new private archive directory. Inspect the observations and planned old→new identity before the explicit apply.

```sh
node scripts/temporal-recover-initial-compatibility.mjs \
  --old-release /secure/failed-staging-release.json \
  --new-release /secure/reviewed-staging-release.json \
  --review /secure/recovery-review.json \
  --archive-dir /secure/recovery-dry-run-UNIQUE
```

After reviewing the dry run, repeat with a different fresh archive directory and explicit `--apply`. This is an operator action; this documentation does not assert it has run. All Firebase emulator overrides are rejected. The command verifies actual original frozen policy/current UI traffic and no pending UI rollout; actual single-region staging Functions inventories/operations; global and us-central1 builds; and us-central1 Cloud Run operations/services. A settled failed latest revision is allowed; active operations or reconciling services block recovery. Failed or incomplete inventories fail closed. Full build histories are checked for active work but archived only as aggregate count/status/hash plus reviewed individual builds.

Before acquiring a lock, apply reads actual queues/tasks, RTDB work, canonical pending/processing admissions and private leases; validates the complete archive including original checkpoint documents against its 750,000-byte budget; and rechecks the fresh review. It then acquires a nonexpiring recovery operation lock using the old release/revision with another exact checkpoint and ancestry comparison. Active, needs_attention, malformed or unknown-outcome leases block recovery, including an independent transactional recheck before commit. Pending canonical rows/queues are recorded and preserved; this checkpoint-only migration deletes or changes none of them and explicitly claims no drain. Previously admitted orphaned work must still be completed or reconciled through the original settling and transactional drain gates.

A subsequent failed initial compatibility attempt may be recovered only while this same original boundary remains frozen. The command walks every protected predecessor archive, validates exact descriptor hashes/UUIDs/source pins, successive revisions, unchanged scope and nondecreasing grace, original frozen traffic and browser identity artifact hash, and exact native original control/state createTimes. Cycles, missing archives and any archive whose native updateTime differs from its createTime are rejected. The genuine original first archive may lack a head hash only when its original boundary and immutable metadata pass the complete bootstrap checks; a multi-hop unpinned head cannot use that exception. New archives pin the predecessor archive hash and chain summary, and the live successor state pins the new archive hash and original identity. Native Firestore timestamps and exact two-key `{seconds,nanoseconds}` equivalents hash identically; timestamp-like objects with extra fields retain those fields and cannot bypass hashing. Independently read archive create/update times are rechecked transactionally before acquiring the operation lock and again before final commit, preventing an archive change between validation and use.

The final transaction compares the original control/state and recovery lock, creates `_control/temporalCompatibilityRecovery-OLD_RELEASE_UUID` with exact old control/state, native original document createTimes, immutable descriptors/hashes, observed runtime/settlement evidence, unchanged frozen traffic, reason and explicit predecessor→successor pointers. It **updates** existing control/state documents in place, increments the revision, sets the new release/source pins, preserves saved UI policy/traffic/freeze request/maximum legacy timeout and keeps `ui-frozen`/legacy/paused. It never creates a cutoff, changes an owner, lowers a deadline, deploys code, removes work or starts dispatch. The own operation lock is removed only in that successful transaction. A failure after lock acquisition retains it for explicit inspected reconciliation; no generic unlock or retry override is provided.

Original 17:35 browser baselines remain historical under the old source/release. Do not rewrite their timestamps or run a fresh open baseline while paused. The preserved original createTime, archive continuity, unchanged paused admissions, same browser actor and separately verified unchanged rules/fixture hashes can support a **separately reviewed** ancestry-aware final browser proof. Existing private helpers pinned to the old release must be explicitly extended after the new identity is known; the checkpoint migration alone does not authorize reuse or fabricate compatibility evidence. Continue using the new descriptor for guarded compatibility deployment, then obtain new genuine compatibility evidence and use normal compatibility-ready/settling/drain/worker/backend/UI gates.

## Frozen split Functions dependency uploads

Each deployed `functions-core`, `functions-media`, `functions-image` and `functions-integrations` source root includes its own committed npm v3 `package-lock.json`. The workspace pnpm lock remains authoritative for local workspace builds; it is outside these Firebase upload roots. An actual successful staging build `b8174eea-67b0-4474-9299-bf067730b989` logged lock generation, `npm install --package-lock-only --quiet`, then `npm ci --quiet --no-fund --no-audit` with `NODE_ENV=production`. The former local startup test used the frozen workspace pnpm graph with lifecycle scripts disabled; the Cloud builder used npm with its normal lifecycle behavior.

After reviewing dependency/catalog/security-override changes, use the npm CLI through the isolated generator; never hand-edit lock entries:

```sh
node scripts/functions-npm-locks.mjs generate
node scripts/functions-npm-locks.mjs check
```

Both commands require Node22. Generation writes only the four lock artifacts, resolving the exact deterministic `materializedPackageContents` manifest in clean temporary directories without parent workspace links or local registry configuration. It uses `npm install --package-lock-only --ignore-scripts`; this is **lock generation only**, not runtime validation. Review and commit the manifests/workspace policy and resulting locks together. Normal deployment checks existing locks and never regenerates them or resolves package ranges.

The generated npm manifest preserves every reviewed flat exact-version pnpm override, including transitive security fixes. Direct overridden dependencies are pinned to exactly the same version as their override, avoiding npm's `EOVERRIDE` while retaining the security decision. Unsupported nested/conditional selectors, removals, aliases and range overrides fail explicitly until an npm equivalent is separately reviewed. A pnpm-only patch present anywhere in the standalone npm graph blocks export; the existing `firebase-functions-test` patch is test-only and absent from these four deployed graphs. No patch is silently dropped from a reachable runtime graph.

Catalog materialization validates all four locks before writing any generated manifests. The source guard independently requires the exact tracked lock bytes and matching materialized declarations from the claimed commit. Only these four actual split deployment roots require npm locks; explicit development `functions/package.json` catalog materialization remains available without an npm deployment lock.

CI copies each actual materialized manifest, immutable lock and compiled library into a fresh directory outside the checkout, runs `npm ci --omit=dev` under `NODE_ENV=production` with normal lifecycle scripts enabled, and checks unchanged lock bytes and absent development-only packages.
