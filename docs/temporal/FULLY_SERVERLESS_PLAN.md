# Fully serverless migration implementation plan

Status: authorized implementation and staging deployment; no production deployment. The human authorization supersedes the earlier deployment hold. Do not resize the worker VM, introduce another always-on host, or retire existing workloads until the replacement and exact handoff have been verified. Latest human scope: retain the existing Hetzner YouTube downloader/authentication for now. Defer residential proxy and home-machine replacement until the human regains access. This is an explicit exception to the serverless compute target, not a prerequisite for Temporal staging readiness.

## Target

- Temporal Cloud retains workflows/history and wakes versioned Cloud Run worker pools through its native serverless integration (Public Preview). Min instances zero, bounded max instances and explicit scale-in stabilization.
- A separate authenticated Cloud Run dispatch service uses the existing outbox leases, stable workflow IDs and unknown-ack handling. Firestore events wake it; bounded scheduled reconciliation recovers missed events, future retries and expired leases. It has no continuous polling loop and scales to zero.
- Keep one immutable pool per role deployment and source build, with one queue and dedicated runner/scaler identities per role. Preserve orchestration deployment name; the other five roles use explicit separate deployments. Reject a consolidated six-queue process: the existing controls runtime explicitly excludes external provider credentials (`scripts/deploy-temporal-platform.mjs`). Native independent-Activity routing supports this separation; verify real application replay and queue handoff before rollout.
- Audio scratch uses explicitly provisioned ephemeral disk; preserve supported input/output budgets and bound media concurrency to actual disk capacity. Store durable inputs/results in the existing same-region bucket. No persistent disk or filesystem is an authority for completed work. Initial media design is one100GiB ephemeral volume perinstance, mediaConcurrency1, a64GiB workspace reservation plus16GiB headroom (80GiB total; source/output budgets are already inside workspace). Require actual approved perinstance/regional quota and statfs evidence before admitting media; no promised storage capacity from configuration alone.
- YouTube acquisition retains the existing Hetzner authentication and recovery service. Serverless orchestration must preserve one task authority, immutable artifact receipts and cancellation/unknown-outcome handling when invoking it. Do not assume the legacy full-processing endpoint is an acquisition-only adapter: verify the boundary before routing a Temporal activity to it. All other eligible task execution targets scale-to-zero compute. No new proxy or home-network changes in this release.
- Preserve familiar UI, authoritative status sources, provider journals, idempotency, cancellation and privacy. Existing public-only provider simulation stays staging-only.

## Native handoff design under review

The Cloud Run integration docs warn against WCI-managed pools sharing queues with traditional workers: periodic scaling counts arrivals already handled by those workers. Do not attach the native scaler while original Kubernetes pollers remain on those queues. The installed Temporal CLI 1.9.1 exposes `worker deployment update-version-compute-config`, including changing the provider of an existing version. This provides a candidate staged handoff without rewriting old pinned code:

1. Prepare the new immutable pool at zero instances with no native compute association. Before any rollout, verify exact source/image, dedicated version runner identity, permissions, media quota and guarded release support. Preserve existing role credential isolation with separate pools/service identities. Do not mount external-provider secrets or grant their Secret Manager access to controls. Prove every role queue is bound to its intended deployment; a role cannot silently join orchestration's version.
2. During the guarded transition, temporarily run each required candidate role pool at one instance as an ordinary versioned worker, with WCI still detached. This is bounded transition compute, not the final serverless state. Prove its real revision/build/queue registrations and preserve normal compatibility/drain/provider/ownership/backend/UI gates. Freeze UI before staging merge as usual. Do not treat a manually running pool as a scale-from-zero test.
3. Prefer original pinned executions finishing or their existing safe continue-as-new protocol. A state-intact execution needing a replay-safe fix may instead use the separately guarded, exact-original-run native Versioning Override described in [the handoff note](ORIGINAL_RUN_SERVERLESS_HANDOFF.md). This requires final application-history replay, native pending-attempt/provider-lease checks, exact target role witnesses and mutation-intent/unknown-ACK reconciliation. Changing current versions alone does not move old shared pinned Activity retries. No override is performed by a readiness check; its live guarded operation is still to be implemented. Preserve held work and unknown outcomes: no reset, repair resubmission, invented migration signal, old-image mutation or premature retirement. Retain old workers until every protected execution is safe and native version-wide drainage is proved.
4. Keep admission paused through this boundary. Require fresh authoritative candidate in-flight activity and dispatch/provider lease readbacks proving the manually running candidate is idle, in addition to full native drain and audited retirement of every traditional poller on the affected queues. If the candidate still owns work or an unknown lease, do not apply initial0 or force a count change. Only after these conditions hold, attach WCI to the existing immutable candidate pool/version using the supported compute-config update. Confirm the version previously had no compute association and preserve image/build/pool/runner identity. Apply all five scaling flags together: min0, initial0, explicit bounded max, utilization and stabilization. The transition must not manually race the WCI's instance count.
5. Verify real zero->task->work->zero, delayed timer/retry wakes, interruption recovery and full business smoke. Connection validation alone proves neither scaling updates nor task processing. Keep existing VM resources until all required handoff/readiness checks pass; cleanup requires its own reviewed normal operation.

This sequence is a proposal requiring source review and a native lifecycle test before live application. It does not authorize a manual shortcut around the controller, a new VM, or a retained one-instance floor. A request for a preferred hosting architecture is not treated as approval to discard pending work.

References: [Cloud Run scaling and queue sharing](https://docs.temporal.io/serverless-workers/cloud-run), [deployment and dedicated runner/invoker identities](https://docs.temporal.io/production-deployment/worker-deployments/serverless-workers/cloud-run). The native CLI help was read locally without contacting a namespace; no configuration was changed.

Two version-specific Eventarc triggers match only written events on immediate documents of `durableJobOutbox` and `durableJobCommands` in the default staging database. It derives an operation ID from the complete immutable staging media reference, reads an existing operation before starting, and reconciles a lost start acknowledgement through the same operation. It never blindly repeats a start within that invocation. A restarted caller can observe an existing running/result record. Cancellation stops polling without asserting the remote process has drained. Returned source observations must use the expected private path, numeric Storage generation and existing positive duration ceiling of86400seconds; actual private request/Storage verification remains the activity's responsibility.

The transport permits only the existing staging Hetzner origin, requests a Google-signed ID token for that audience, rejects a static credential-file override, disables redirect following and uses single HTTP sends. Its10-second cancellation-aware budget includes credential discovery, token creation, HTTP and bounded16KiB body reading. A late authentication result cannot initiate a POST after cancellation. Pending credential setup is shared until it settles. Provider/HTTP exceptions are replaced with generic failure messages. Hetzner must independently validate the signed token's issuer, audience and exact permitted media-runner identity; Cloud Run IAM does not authenticate a Hetzner target. See [Google service identity and ID tokens](https://docs.cloud.google.com/run/docs/authenticating/service-to-service).

The private host-operation store now provides atomic native-prepared delegation, one-owner claims, no time-based takeover and drain-before-settlement. Both preparation and host storage reject a Firestore instance outside staging. A required transaction guard must be wired to the real native Activity authorization before preparation; the host eligibility guard must inspect canonical ownership/cancellation/release/source state. Emulator transactions prove store atomicity, not these future production guard integrations. Client rules deny the private collection even to browser administrators. The helper records private source receipts only; canonical source adoption belongs to the real native Activity under its own current authority. The actual host HTTP/process driver, native restart reconciliation, canonical cancellation observer, shared-disk reservations and continuous byte limits, Storage verification/adoption, and same-host fresh authentication canary still require implementation and integration tests before activation. The existing loopback-only canary endpoints stay loopback-only. File uploads must retain their local serverless pipeline. The fresh-recovery contract must also define how a drained authentication/archive-deferred operation becomes eligible again after new authoritative evidence; polling a permanently stored waiting result is not sufficient. ### Retained acquisition subprocess drain boundary

The host-only `runYouTubeAcquisitionProcess` foundation starts a compiled acquisition helper in its own POSIX process group. IPC carries only the validated immutable reference, operation identity and operation-owned local workspace. Standard output/error are discarded rather than entering task history. Cancellation and a bounded host deadline terminate the whole group, including downloader descendants; termination escalates after five seconds. Even a successful direct-child exit is rejected as a failed execution if descendants remain, and the group is drained before a failed outcome can return. Confirmed drain returns only `completed`, `cancelled` or `failed`; uncertain drain rejects and the host must keep its durable resource reservation fenced. A completed subprocess is not a source artifact or task-completion receipt.

Local native-process tests cover ordinary completion, cancellation with a descendant, a child that ignores termination, leaked descendants, pre-cancellation and diagnostic isolation. This is not the actual acquisition helper/bootstrap, canonical cancellation observer, cross-container resource coordinator or native Hetzner proof. Those integrations and actual host filesystem/process evidence remain activation prerequisites; the function is not wired to a route or worker.

### Private streaming upload journal and native Storage transfer

The concrete upload engine now uses the native Cloud Storage client with CRC32C validation, 1 MiB resumable chunks, generation-create preconditions and disabled write retries. It meters bytes through a backpressured Transform and refuses empty or over-20-GiB streams. Uploads carry immutable operation/job/request/attempt metadata. An owner-fenced Firestore transaction creates each private upload intent before producer launch; one unresolved attempt prevents another attempt or same-ID producer replay. Strict state shapes distinguish a running stream from verified complete bytes and retained object receipts. Only complete input with successful producer completion and confirmed drain can record its expected size/checksum. Final acceptance checks the same object's native metadata and preserves its exact generation. Unknown complete-upload acknowledgements reconcile by reading that same object, with no provider replay or new upload.

Dedicated emulator tests use actual Firestore transactions and the native Storage streaming client. They cover byte/checksum/object-generation readback, reconciliation without producer restart, partial/failed producer rejection, unknown-drain fencing, revoked eligibility, corrupted journal states, concurrent distinct-attempt exclusion, silent-producer cancellation and missing immutable object metadata. The producer/drain callbacks in these tests are controlled stream fixtures; native child-group, filesystem/scratch, memory, long-provider-download and production Storage behavior remain separate required evidence. Tests exposed and fixed a state-corruption path that previously let a streaming record claim completed bytes. A second real regression caught cancellation after the upload had completed while its producer had not exited; an independent cancellation listener now remains until native completion/drain, and an unknown drain rejects without waiting forever for producer completion.

This transfer is not yet the acquisition child/bootstrap or an activated route. Unknown native attempts remain fenced. Confirmed native failure now permits a fresh isolated attempt only when its bounded transfer fulfilled and native drain succeeded; independent transfer rejection never grants authentication fallback. The native sink now connects this classification to the existing authentication ladder, but the real bootstrap/resource/Activity integration remains required. No reset or timeout takeover may clear an uncertain attempt. Native source adoption, actual duration measurement and the same-host authentication canary also remain unconnected. The dedicated test command uses the same experimental VM-module flag already present in the repository's Functions test script, required by the native Storage client's dynamic imports. SDK-internal PassThrough listener warnings were traced to teeny-request's pipeline composition; they were not suppressed and do not count as proof of deployed memory bounds.

Official upload behavior references: [Cloud Storage retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy), [data validation](https://docs.cloud.google.com/storage/docs/data-validation), and the [native Node Storage stream implementation](https://github.com/googleapis/nodejs-storage/blob/main/src/file.ts). The implementation relies on its own counted checksum and metadata verification for ambiguous upload completion, rather than treating SDK stream closure as canonical source adoption.


### Native Linux acquisition byte producer

The retained-host byte producer now starts a real child process whose stdout feeds the upload boundary. It requires Linux, an isolated per-operation helper with its own process group/session, a real tmpfs of at most 256 MiB, an owned non-symlink directory with mode 0700, and working native pidfd open/signal-zero calls before launching the producer. Child temporary/cache locations point into that workspace. Diagnostics remain private and bounded to 64 KiB; truncated diagnostics cannot be presented as complete authentication evidence.

A private Python drainer verifies the helper's native process birth/session, inspects its process-group members, and uses pidfds with identity rechecks to avoid signalling reused unrelated PIDs. Termination escalates after five seconds and fails closed if group drain cannot be confirmed. Direct-child exit starts drain before waiting for pipe closure, so a surviving descendant holding stdout cannot hide behind an exit-zero result. Leaked descendants are drained and cause failed completion. Leftover attempt processes are drained and reject a new launch. This scope assumes the pinned yt-dlp/FFmpeg descendants inherit the isolated helper group; detached/daemonizing producer tools are unsupported. It is not permission to launch arbitrary binaries from HTTP or run this module in the shared server's process group.

The operator fixture at `apps/process-audio/scripts/test-youtube-acquisition-producer-linux.cjs` runs the current source in an existing, inspected immutable local Linux image. It pulls nothing, has no network or credentials, mounts only owned fixture files read-only, uses a bounded tmpfs/memory/process count, and removes its named container in a finally block. Native scenarios prove output, failed exit, leaked descendants, cancellation/escalation, leftover-process fencing, filesystem/session denial, private directory permission denial and bounded diagnostics. Actual amd64 emulation lacked pidfd syscalls; the activation preflight correctly rejects it before provider launch. Native ARM64 Linux passed the producer scenarios. A separate read-only check inside the existing staging Hetzner container confirmed pidfd support on its x86_64 Linux 6.8 kernel as uid 1000; it sent only signal zero to its own process and did not execute the new producer there.

These are local native mechanics and a production-kernel capability check, not deployed producer, provider download, shared-host memory capacity or full readiness evidence. The real helper bootstrap, durable owner authorization before execution, shared-host reservation/continuous checks, upload failure classification/fresh isolated attempts, canonical cancellation observer, authentication canary, OIDC route and native Activity source adoption remain required. The existing full-file pipeline and its resource guards remain intact.

### Native helper identity and claim integration
