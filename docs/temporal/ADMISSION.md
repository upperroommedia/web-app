# Trusted durable admission

The browser submits business intent to `submitDurableJob`. Firebase verifies the current Auth user, normalizes the domain payload against canonical source records, and commits an immutable private intent, public projection, resource generation and broker outbox together. No browser has Temporal credentials or writes progress or provider IDs.

`requestId` identifies a single immutable input. Receipts are scoped by project and authenticated UID; concurrent identical requests converge on one receipt. Changing input under an existing ID fails. `getDurableJobReceipt({requestId})` recovers an uncertain response without repeating the operation. Invite claim URLs exist only in the submitting user's authenticated receipt/private intent, never in workflow history or public projections.

Each domain is gated with `TASK_ORCHESTRATOR_<DOMAIN>=temporal`. Admission rejects inactive domains rather than leaving unowned work queued. Media ownership also checks actual RTDB legacy request/lock/deferred namespaces. Staging cutover must drain legacy queues before enabling gates. Rollback must not activate legacy workers while Temporal owns the same resources.

The private `_control/temporalRelease` document supplies the authoritative owner and admission pause for each domain. New admissions read it in the same transaction as their resource reservation. Temporal admission requires an explicit Temporal owner and open admission; missing control fails closed. A previously admitted receipt, source confirmation or operator command remains recoverable during a pause. Trusted bundle bootstrap also fences the exact release ID and control revision.

Legacy callable effects hold a durable `legacyAdmissionLeases` record acquired atomically with the control check. Handlers acknowledge `markEffectsStarted()` before their first mutation and heartbeat until completion. A crash, expired heartbeat, thrown error or returned failure after effects leaves a blocking lease for review; expiry never proves that an external operation stopped. The release tooling checks these records alongside the actual legacy queues and locks. Closing an uncertain lease requires stopped execution, concrete verification evidence and an immutable private review audit.

Media drain also counts canonical `PENDING` and `PROCESSING` admissions while media remains legacy-owned, including browser uploads whose bytes have not arrived and YouTube downloads. Ownership transfer rechecks these rows in its control transaction; no client-shaped durable marker exempts them. A verified initial source trigger can finish pre-existing work during pause by rechecking canonical owner, range and pending status in its lease transaction. At compatibility readiness, the release records `legacyAdmissionCutoff` once using a server commit timestamp. Sources created during the initial freeze-to-compatibility window remain valid; later paused continuations require canonical `createTime` at or before that cutoff. Subsequent checkpoint timestamps never extend it. Abandoned sources remain visible and block cutover until explicitly completed or reconciled.

## Upload handshake

1. Admission creates a canonical sermon and an `awaiting_source` job/session. The server chooses `durable-upload-sources/<uid>/<jobId>/source` and records immutable file size/fingerprint. No workflow is dispatched before bytes exist. Selected lists and series are attached locally in the same transaction, with unpublished mirrors and consistent counts; this never publishes to external providers. Series positions are allocated while holding the canonical series transaction fence.
2. The browser uploads bytes once with `durableJobId` and JSON `fingerprint` object metadata. Storage rules enforce UID/path/reserved size and prohibit overwrite/delete. Transfer progress reflects browser bytes only.
3. `resume_upload` submits the exact object generation. The server verifies that generation, object size and job/fingerprint metadata. It derives source and bumpers from canonical records, not client provider URLs.
4. Media admission atomically checks the upload's cancellation state, creates the durable audio intent/outbox and confirms the source job/session. Cancellation and confirmation cannot both win. The source job's `succeeded` state means source admission completed; `result.mediaJobId` is the processing job which the UI follows.
5. Retrying a lost acknowledgement reuses the deterministic child identity. A reload before upload completion requires the original file to be reselected and fingerprint matched. A tab may close safely only after durable source confirmation; file bytes cannot be transferred by Temporal from a closed browser.

An explicit retry after a failed or cancelled source-only attempt submits a fresh `upload.create` request with `retryOfJobId`. The server derives the existing sermon from that user's original private admission, verifies the original source fingerprint and range, and creates a new immutable source path and upload generation. Canonical metadata, list and series selections are retained without duplicate mirrors or counters. A newer source owner, prior audio ownership, pending deletion, publication or unresolved publishing attempt blocks the retry. Already confirmed audio is followed through its audio job; factual completed audio returns private `clientResult.alreadyComplete` navigation instead of admitting another upload. An uncertain retry acknowledgement retains the same fresh request ID.

## Commands

`commandDurableJob` validates the authenticated actor, advertised action, projection revision and domain ownership. Command IDs are immutable and scoped per caller. Cancellation remains `cancel_requested` until the worker confirms termination/cleanup; pending source uploads can be cancelled atomically without a workflow. Singleton media coordinators receive a targeted cancellation signal rather than cancellation of all processing for that sermon.

Commands use private `durableJobCommands` records. The private dispatcher leases records and acknowledges them only after Temporal accepts the signal/cancellation. Repeated delivery is expected and domain signals/receipts must be idempotent. Provider ambiguity requires an admin-reviewed domain resolution, never a blanket retry of a create request.

Verified provider resolution, its review audit, command outbox and public revision change commit in one transaction. Resource generation fencing prevents an old job from resolving into a newer owner. Account changes allow cancellation only while queued; once claims work begins, the workflow must finish or enter reviewed recovery rather than report a cancellation while permissions may already have changed.

Sermon edits freeze canonical list membership and publication state at admission and recheck it before effects and final projection. Edit membership writes are bounded to a conservative 450 mutations. Deletion has no membership-count admission cap: the worker captures and seals a paged private ledger of the complete managed canonical root, overflow and series graph before effects, subject to its actual byte budget. The critical transaction requires complete provider-reference coverage and fresh exact destination-count proof, so late mirrors block the first provider deletion and large catalogs can be cleaned in bounded pages. This authority covers the captured managed graph; it does not infer arbitrary manually created provider memberships. Client provider IDs, URLs, published ordering and entity labels are discarded. Activity labels come only from bounded canonical titles or names and never include account email addresses, invitation tokens or mail content.

## Access and verification

Public jobs are readable by the requesting user, canonical user target for account outcomes, admins, and the owner of a canonical sermon when observing that sermon's referenced job. Publishers do not gain a global activity feed for other users. All private intent/outbox/receipt/session/command, execution and review collections deny browser access. Server-side role checks are repeated before activities perform effects; cached client claims do not grant continuing authority.

`sourceSessions.test.ts` covers source identity/fingerprint/generation checks. `admission.integration.test.ts` covers concurrent deduplication, input immutability, receipt scope, disabled accounts, command revisions and the source-confirmation/cancellation race. `admission.rules.test.ts` exercises server-authored projections and immutable uploads with real Firestore/Storage rules. Emulator suites must run through `firebase emulators:exec --config ../firebase.test.json`, one harness at a time.
