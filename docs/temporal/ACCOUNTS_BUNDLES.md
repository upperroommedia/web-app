# Account access, notifications, and bundles

Account workflow history contains only `{ projectId, jobId }`, step identifiers, and safe state codes. Authorized admission stores recipient addresses, invitation URLs, speaker payloads, and resolution messages in the private Firestore intent collection. The worker reloads that intent at each activity and rechecks the actor's current Firebase Auth role and entity generation before new account effects. After a proven grant or external mutation, restricted completion can still revoke sessions and record the outcome if the approving actor later loses permission; it cannot grant another role or create another resource.

The account workflow validates, applies claims, revokes sessions, creates the requested speaker where applicable, commits the resolution document, then queues the notification. Claims merge unrelated custom claims; invitation claims preserve a higher existing role. Claims and session revocation each retain a single-shot mutation receipt and a persisted source checkpoint. A crash after sending either request cannot authorize another remote write: an uncertain result remains blocked until its originating execution is drained and a fresh Auth read positively proves the exact frozen operation. Session proof includes the unique operation marker, complete frozen claims and revocation cutoff; an existing cutoff alone is insufficient. Source records hold stable speaker mutation results and deterministic mutation keys. External speaker creation does not have automatic activity retries: ambiguous provider effects require reconciliation.

Direct administrator role changes use `role.assign` with the canonical Auth user ID; each private assignment record checkpoints merged claims and session revocation. Role/speaker request admission must transactionally reserve the pending request with `temporalJobId` and create its intent/outbox. Competing accept/deny operations cannot both reserve a request. Role and invitation claims must serialize using the target user entity, not just the request document. Invitation claim admission still validates the token hash, owner email, expiry, and revocation before reserving `ROLE_PENDING`; no raw token enters Temporal. Activities reject revoked/expired unconsumed claims and changed permissions before grants. Revocation transactionally refuses active claim reservations and already-applied grants; administrators change the user role explicitly after a grant. Completed invitation replay never restores a privilege after a later administrator role change. Reviewed new requests may take over only terminal cancelled, failed, or superseded source reservations whose private per-user mutation resource has no pending or uncertain claims or session phase. A terminal job alone cannot release an ambiguous Auth request. Existing Firebase authorization/security handlers remain synchronous.

In Temporal ownership mode, new role/speaker requests and all associated mail documents commit in one Firestore transaction. A transactionally coupled pending-request pointer prevents simultaneous retries from creating another request or another notification. Failed commits leave no orphan request.

`queueEmail` accepts an optional `idempotencyKey`. It hashes that logical identity into a stable mail document ID and creates the document transactionally only if absent. Existing callers without a key retain random-ID behavior. Outcome activities use `account:<jobId>:notification`; retries cannot reset existing delivery state, replace a delivered message, or enqueue duplicate outcome documents. SMTP delivery is a separate workflow and must handle an ambiguous acceptance result explicitly; durable orchestration cannot guarantee exactly-once email delivery.

The bundle coordinator receives `requestBundleRegeneration` signals containing private job references. Each predefined bundle configuration has one coordinator per project. Activities write immutable per-attempt artifacts, then commit the canonical Firestore generation pointer in the same transaction as the entity fence. The RTDB cache updates only to an equal/newer generation; serving resolves the canonical pointer. Timed-out attempts cannot overwrite a newer artifact or pointer. A durable 2.5-second timer coalesces changes; signals received during generation queue another cycle. There is no process-local sleep, expiring ownership heuristic, or fixed cycle cap in Temporal. Continue-As-New bounds history, and the coordinator closes after 30 seconds idle so old pinned workers can drain during deployments. Signal-With-Start admits the next event into a fresh execution. Duplicate signal IDs are ignored, and each generation cycle resolves the current desired job from the authoritative entity record, so delayed signals cannot replace a newer queued generation. Trusted source events may finish during an admission pause; fresh public cache misses return `503` with `Retry-After`. The release controller invokes the [six-bundle bootstrap](BUNDLE_BOOTSTRAP.md) and verifies successful immutable artifact convergence before opening new admissions. Firebase remains the event ingress and serves existing bundle objects/metadata, so clients keep their URLs, RTDB metadata fields, and Firestore listeners.

Old grant/approval/invitation-email callables reject with a refresh-required error once Temporal owns accounts; the new UI uses the durable admission facade. Legacy invocations register a durable release-control lease before running, acknowledge that lease immediately before their first effect, and remain visible until completion. A returned legacy error after an effect retains a `needs_attention` lease rather than falsely declaring the work drained. Compatible local request creation and revocation keep their response shapes and transactionally observe the owner/admission pause.

Legacy handlers retain ownership until the domain ownership record is cut over and old in-flight work is drained. No live changes are made by local development or tests. Reject all caller-supplied arbitrary bundle query paths; worker activities resolve a bundle type against the static shared configuration allowlist.

References: [Temporal message passing](https://docs.temporal.io/develop/typescript/workflows/message-passing), [Continue-As-New](https://docs.temporal.io/develop/typescript/workflows/continue-as-new), [activity idempotency](https://docs.temporal.io/activity-definition), and [TypeScript activities](https://docs.temporal.io/develop/typescript/activities).

Account canonical checkpoints and notification outbox transactions share the job generation and Activity execution fence. Auth role updates additionally acquire a private per-user resource before calling Auth. An unacknowledged call retains its owner without expiry, even if the job or Activity is superseded; competing grants and automatic repeats remain blocked pending privileged reconciliation of a drained execution and authoritative Auth claims. The private frozen claims include a job marker so acknowledgement can be proved without guessing from the role alone.

Temporal claims mutations use one authenticated Identity Toolkit REST POST through native fetch, with redirects disabled and a bounded deadline. Admin SDK implicit request retries are excluded from this path. The resource records `transport: single_shot_identity_toolkit`; positive acknowledgement reconciliation requires this protocol plus the originating execution drain witness. See the [official accounts.update contract](https://cloud.google.com/identity-platform/docs/reference/rest/v1/projects.accounts/update) for `localId`, JSON `customAttributes`, and OAuth scope. Local Auth emulator routing follows the Admin SDK emulator endpoint and never falls through to production.

Session revocation also uses a single Identity Toolkit POST. The confirmed-claims transaction freezes `sessionCutoffSeconds` and reserves the UID's pending session phase. Only a proven unsent or structurally rejected request may retry, reusing the same frozen cutoff, session operation UUID and complete custom claims. An uncertain sent revocation remains `sessionState: started` without automatic replay. Confirmation requires a bound execution drain witness, a fresh `tokensValidAfterTime` at or beyond the cutoff, and exact full Auth claims containing this request's unique `temporalAccountSessionOperationId`. No earlier or later cutoff without that marker can settle the request. New grants cannot overtake pending or uncertain session cleanup. A positively unsent request can release only its exact execution reservation while preserving the cutoff. Frozen custom claims are checked for reserved keys and the 1000-byte limit, including the job acknowledgement marker, before acquiring a mutation resource.

A completely received response from the official Identity Toolkit TLS endpoint can release a resource only when its structured Google RPC `error.code` and `error.status` exactly match the documented validation/authentication/permission/not-found rejection. The private receipt records `rejected_no_effect` with its fixed rejection code; it never stores raw error bodies. HTML proxy errors, mismatched codes, timeouts, lost acknowledgements, and 5xx responses remain unknown. Canonical codes follow the [Google API error model](https://cloud.google.com/apis/design/errors).

A session operation writes a unique `temporalAccountSessionOperationId` within frozen custom claims atomically with `validSince` in that same POST. A pre-existing equal or later cutoff alone cannot confirm an uncertain request. Recovery additionally requires the fresh Auth claims to exactly equal the private frozen session payload and unique marker, plus the originating execution's drain proof; old unmarked receipts fail closed. A fresh target-claims comparison immediately before sending prevents the cleanup payload from overwriting access or unrelated claims changed during credential refresh.
