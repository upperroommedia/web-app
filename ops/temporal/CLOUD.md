# Temporal Cloud with one GCP worker VM per environment

Use single-region Temporal Cloud in GCP `us-central1`, matching both Firebase App Hosting backends. Run application workers on one GCE VM per Firebase project. This is the selected low-volume configuration: no replicated worker fleet, GKE control plane, Temporal server, PostgreSQL, PITR or disaster-recovery infrastructure.

| Project           | Full Temporal namespace | Worker VM                 | Region            |
| ----------------- | ----------------------- | ------------------------- | ----------------- |
| `urm-app-staging` | `urm-app-staging.qwejt` | `urm-temporal-staging`    | GCP `us-central1` |
| `urm-app`         | `urm-app.qwejt`         | `urm-temporal-production` | GCP `us-central1` |

`qwejt` is the account ID assigned by Temporal in the full namespace name. The application names remain `urm-app` and `urm-app-staging`. Prefer the exact namespace endpoints `urm-app-staging.qwejt.tmprl.cloud:7233` and `urm-app.qwejt.tmprl.cloud:7233`; the trusted regional endpoint `us-central1.gcp.api.temporal.io:7233` is also supported. Neither endpoint configuration claims that cross-region replication is enabled. See [regions](https://docs.temporal.io/evaluate/cloud/regions) and [API keys](https://docs.temporal.io/cloud/api-keys).

## Simple worker host

Each VM uses `e2-standard-4` (4 vCPU, 16GB RAM) in `us-central1-a`, the attached service account `temporal-worker@PROJECT.iam.gserviceaccount.com`, and Application Default Credentials. No Firebase/GCP service-account JSON key is created or mounted. Single-node K3s provides supervision and preserves the existing real Pod, Node, cluster UID, container image, SDK instance and worker-drain witnesses. It hosts one replica per role, with independent controls polling. Native media concurrency is one, reserving one CPU; each other role requests 250m CPU. Inputs and published artifacts remain in Firebase Storage, while native scratch is local to the reviewed dedicated disk.

Use `environments/staging.cloud.example.json` and `production.cloud.example.json`. Replace placeholders with actual VM instance ID/private IP, K3s cluster UID/Node name, immutable image digest/full commit, actual service443/private API6443 endpoints, runtime credentials and proof files. The descriptor and deploy preflight verify actual Compute instance identity and its attached account. They do not infer a cluster or Pod identity from a VM name. Rendering is offline; it provisions nothing.

Staging can deploy first with `production.cloud.planned-peer.example.json` as `--peer`. That descriptor contains only the planned production project/full namespace/account/region/hosting identity, with `deploymentState:planned`; it contains no invented VM, context, cluster UID or evidence. It cannot serve as a deployment target. An already-deployed peer must provide its actual descriptor and pass live Compute/Kubernetes identity checks. Production infrastructure is not required merely to validate a staging deployment.

The media storage class is `temporal-media-local`, using K3s local-path provisioning only at `/var/lib/urm-temporal/media`. That directory must be a separate mounted ext4 filesystem. Each scratch claim requests100Gi; total quota is 400Gi to cover retained versions and release surge. Source/output limits remain 20Gi, workspace 64Gi and free headroom 16Gi. GCE disk sizes use GiB even when the CLI accepts the `GB` suffix. Allow room for filesystem metadata/reserved blocks and prove the actual mounted filesystem covers400Gi. Staging uses an actual470GiB balanced disk and verified ext4 capacity;500GiB remains an example rather than a requirement. Local-path is allowed only under this explicit single-host descriptor; the self-hosted and optional GKE modes retain their CSI restrictions.

One host can be offline during maintenance. Temporal Cloud retains durable work until workers return. This does not relax original provider acknowledgement, uncertain-mutation barriers or application recovery rules. A full old/new worker version overlap can exceed 4CPU. Deployment checks actual Running/Pending pod requests plus the new version before applying it; either drain the old version with admission paused, or explicitly review capacity on the same VM before an upgrade. Never delete an old pinned queue merely to make the scheduler fit.

## IAM and networking

The attached VM account needs application permissions scoped to its own project/resources:

- `roles/datastore.user` for durable jobs, canonical data and private source/evidence records;
- `roles/firebaseauth.admin` for current actor reads and authorized account/claim lifecycle tasks;
- `roles/firebasedatabase.admin` where the retained RTDB adapters require it;
- `roles/storage.objectAdmin` on the actual configured Firebase Storage bucket only;
- `roles/secretmanager.secretAccessor` on `TEMPORAL_WORKER_API_KEY` and `TEMPORAL_OPERATOR_API_KEY` only, plus explicitly inventoried provider secrets if the runtime loader reads them from Secret Manager;
- repository read access only if a private Artifact Registry image is selected.

Do not grant Editor, project-wide Secret Accessor, Compute Admin or Temporal account administration to the application account. VM provisioning/inspection and namespace administration use the human operator's separate identity. The single host is one application trust boundary; external provider credentials are still supplied only to the relevant role's runtime Secret. Controls receive no Subsplash, SoundCloud, Algolia, SMTP or YouTube credentials. Both project bindings are explicit; runtime initialization rejects a contradictory/default Firebase project.

If native YouTube acquisition uses an authenticated Cloud Run browser fallback, grant `roles/run.invoker` on that exact service. If its browser profile lives in a separately configured bucket, grant `roles/storage.objectViewer` on that bucket. These are conditional permissions; the native worker does not require Cloud Functions Invoker, FCM administration, bucket administration or service-account Token Creator.

Create a dedicated custom VPC/subnet in each project. Set reviewed `applicationEgressCidrs:["0.0.0.0/0"]` for dynamic Cloud/GCP/provider endpoints; the rendered application rule permits only TCP443 and Temporal TCP7233. DNS, Kubernetes API, the exact metadata endpoint, and reviewed email transport retain their separate narrow rules. Do not pin transient public DNS answers as permanent provider allowlists. For the simple outbound path, a public IPv4 can provide internet egress while **all public inbound ports remain closed**. Permit SSH22 only from Google IAP's `35.235.240.0/20` to the tagged worker VM, require OS Login, and block project SSH keys. Do not add 6443, NodePort, health or metrics ingress from the internet. Bind K3s to the VM's private IP; use authenticated IAP SSH forwarding for administration. A VM without an external IP is also possible but adds Cloud NAT infrastructure/cost.

Reviewable creation flags (fill the already-created subnet/private address and project; run as the provisioning operator):

```bash
gcloud compute instances create urm-temporal-staging \
  --project=urm-app-staging --zone=us-central1-a \
  --machine-type=e2-standard-4 --image-family=debian-13 --image-project=debian-cloud \
  --service-account=temporal-worker@urm-app-staging.iam.gserviceaccount.com \
  --scopes=cloud-platform --subnet=REVIEWED_STAGING_SUBNET --private-network-ip=REVIEWED_PRIVATE_IP \
  --boot-disk-size=30GB --boot-disk-type=pd-balanced --tags=urm-temporal-worker \
  --metadata=enable-oslogin=TRUE,block-project-ssh-keys=TRUE \
  --shielded-secure-boot --shielded-vtpm --shielded-integrity-monitoring
```

Create/attach the separately labelled scratch disk sized to cover400Gi of actual mounted capacity before formatting or mounting it. Preserve an existing filesystem; initialize only a confirmed blank new disk. Use its stable `/dev/disk/by-id/google-...` name/UUID in the root-owned mount configuration. Install the reviewed K3s version from `versions.json` using the official release and verified checksum, with secrets encryption enabled, private bind/advertise/node IP, no Traefik/service load balancer and root-only kubeconfig. Configure the local-path provisioner to use only the dedicated mount, and create the reviewed storage class with `Delete` reclaim and `WaitForFirstConsumer`. Production uses the equivalent explicit project/instance names; never reuse staging credentials or clusters.

The dedicated offline bootstrap generator is `scripts/temporal-single-vm-config.mjs`; do not use the self-hosted HA generator for this path:

```bash
node scripts/temporal-single-vm-config.mjs \
  --project urm-app-staging --instance-name urm-temporal-staging \
  --instance-id ACTUAL_NUMERIC_INSTANCE_ID --private-ip ACTUAL_PRIVATE_IP \
  --output /private/staging-single-vm-bootstrap
```

Review its `bootstrap.sh`, then copy the bundle to the verified VM and run it as root after the dedicated disk is mounted. It verifies VM metadata, actual filesystem size and the pinned official binary checksum before installation. All local Kubernetes calls explicitly address the private VM IP because a default loopback kubeconfig would not reach a private-only bind. The storage setup unit reapplies the dedicated local-path configuration after K3s restarts. The generated files contain no keys, database, private VIP, additional nodes or backup requirement.

## Mounted Temporal credentials and rotation

Temporal runtime accounts have namespace **Write** access to only their own full namespace. Operator routing/status/retirement uses an independent namespace-scoped Write account and key; account/namespace administration and search-attribute bootstrap use the human Cloud CLI. Keys are stored in their respective GCP projects as `TEMPORAL_WORKER_API_KEY` and `TEMPORAL_OPERATOR_API_KEY`.

`scripts/temporal-vm-secrets.mjs` runs as root on the actual reviewed VM. It verifies metadata project/instance ID/attached account, retrieves only those two keys with the short-lived attached account token, verifies Secret Manager payload CRC, and updates the two K3s Secrets through process stdin. Secret/token values never appear in arguments or logs. The same timer refreshes `temporal-artifact-registry`, a short-lived OAuth pull Secret for `us-central1-docker.pkg.dev`, using only the attached VM token and explicit Kubernetes namespace. Grant repository-scoped `roles/artifactregistry.reader` on the approved `urm-temporal` repository; no registry administrator permission, static Docker token or service-account JSON key is used. K3s secret encryption must be enabled. The client uses an explicit writable cache under `/run/urm-temporal-key-sync`; the default root home remains protected. Runtime workers mount `/run/temporal-cloud/api-key`; operators mount the separate operator key. Keys never reach the frontend or Firebase admission handlers.

Install `single-vm/temporal-key-sync.service` and `.timer`, the script at `/opt/urm-temporal/scripts/`, reviewed Node22 at `/usr/local/bin/node` (a symlink to the verified `/opt/urm-temporal/node-v22.22.0` distribution is supported), and root-owned `/etc/urm-temporal/identity.env` with only these nonsecret fields:

```text
FIREBASE_PROJECT_ID=urm-app-staging
TEMPORAL_KUBERNETES_NAMESPACE=temporal-staging
GCE_INSTANCE_ID=ACTUAL_NUMERIC_INSTANCE_ID
```

The timer refreshes every 120 seconds. Enable/start it only after K3s, namespace and project-scoped Secret Manager permissions exist. Initial keys expire after 90days. Issue replacement scoped keys before expiry, store new Secret Manager versions, verify the mounted file change causes the runtime to drain/restart safely and that the original SDK instance is stopped, then revoke old keys. The timer synchronizes versions; it does not create Temporal keys or extend their expiration. Record key IDs/version/expiration metadata privately and schedule renewal ahead of the actual expiry. Confirm the timer's last successful run and live worker readiness after rotation.

Manual renewal follows this sequence:

1. Inspect the existing account's exact namespace scope and current key expiration privately. Use authenticated `tcld apikey create --service-account-id SCOPED_ACCOUNT_ID --name REVIEWED_ROTATION_NAME --duration 90d`, capturing its one-time secret in the provisioning process rather than printing it.
2. Feed the captured secret directly to `gcloud secrets versions add TEMPORAL_WORKER_API_KEY --project EXACT_PROJECT --data-file=-` through stdin. Use the independent operator account and `TEMPORAL_OPERATOR_API_KEY` for operator renewal. Record only nonsecret key IDs, versions and expiration timestamps.
3. Run/inspect the VM key-sync unit or wait for its next 120-second cycle. Verify the new mounted version, actual old SDK drain, stopped original process and restarted worker readiness/routing. Existing operator jobs must finish before their old key is revoked.
4. Revoke the old key with authenticated `tcld apikey delete --id OLD_KEY_ID` only after those checks. Disable obsolete Secret Manager versions according to the recorded successful rotation. A failed replacement remains recoverable because the old key stays valid through verification.

### Email configuration materialization

Copy the selected project's reviewed kit settings into the email-only runtime Secret: `AUTH_TYPE=UsernamePassword`, `SMTP_CONNECTION_URI`, `DEFAULT_FROM`, `DEFAULT_REPLY_TO`, `MAIL_COLLECTION=mail`, `DATABASE=(default)`, `USERS_COLLECTION`, `TEMPLATES_COLLECTION`, `TLS_OPTIONS`, `TTL_EXPIRE_TYPE=never`, and `TTL_EXPIRE_VALUE=1`. Empty optional user/template collections are supported; empty `TLS_OPTIONS` uses secure defaults, or use `{}` explicitly. Verify `SMTP_CONNECTION_URI` has the reviewed host, port and username and matches `/run/email/egress.json`; treat the URI as secret if it includes a password. `LOCATION`/`DATABASE_REGION` describe the existing kit configuration and are not new worker hosting choices.

The Node worker reads the **canonical environment variable `SMTP_PASSWORD`**. It does not resolve `FIREBASE_SECRET_REF_SMTP_PASSWORD` into a value. Load the approved secret payload through memory/stdin and set the Kubernetes Secret's `SMTP_PASSWORD` field; never place its payload in command arguments, logs, committed files or workflow arguments. Staging currently has the newer `FIRESTORE_SEND_EMAIL_SMTP_PASSWORD` name and the older `firestore-send-email-SMTP_PASSWORD` alias. The checked-in kit exports reference the older names, including production version `1`. Review the chosen project, alias and enabled version before materialization; do not assume the old reference is current or that staging and production share a password.

Use the reviewed Gmail descriptor `{"schemaVersion":1,"provider":"smtp","hostname":"smtp.gmail.com","port":465,"tls":"implicit","dnsMode":"public-ipv4"}` for its rotating public DNS; omit the old literal `addresses` field. The hostname must still exactly match the configured SMTP credentials. The worker validates every current DNS answer, rejects private/reserved or mixed unsafe answers, connects to a chosen IPv4 literal and preserves the original strict TLS hostname. The email-only port policy and HTTPS base policy exclude private/reserved IPv4 ranges; generic HTTPS cannot override those exclusions. Static reviewed public-IP descriptors remain supported with absent `dnsMode` or `dnsMode:"static"`. OAuth/SendGrid use the same explicit mode and literal-IP HTTPS binding. See [email transport policy](../../docs/temporal/EMAIL.md). Re-render/redeploy reviewed worker policy and descriptor together, then repeat the same actual no-send canary; a source-only test is not a live credential or connectivity proof.

The password-URI path does not require OAuth-only `HOST`, `USER`, `CLIENT_ID`, `OAUTH_PORT`, or `OAUTH_SECURE` settings. If OAuth2 is intentionally selected later, inventory the actual `CLIENT_SECRET` and `REFRESH_TOKEN` Secret Manager mappings and reviewed token endpoint egress separately. Production must not use `TESTING=true` or `TEMPORAL_EMAIL_ALLOW_LOCAL_SMTP=true` to bypass the provider binding.

### Initial isolated proof and provider rotation

`sideEffectsDisabled:true` is a statement supported by collected recovery evidence, **not a runtime environment switch**. Keep application admission closed and `TEMPORAL_DISPATCHER_ENABLED=false`. Start the reviewed zero-activity `WorkerRestartProbe` with a unique workflow ID on the existing `urm-orchestration` queue in the otherwise empty staging namespace; arbitrary queue names are not accepted by the worker. Promote the reviewed worker version first so the versioned poller can receive this probe. Do not resume an application job, attach production entities, or invoke a provider activity. Withhold vendor credentials. Email startup still requires a valid matching descriptor/transport configuration, but this proof must not run email verification or delivery. Record actual original workflow/run, worker restart, new SDK instance and resumed original execution before marking the proof passed. These precautions do not claim disaster recovery.

The VM key-sync timer only refreshes mounted Temporal keys and the registry pull token. It does not load or rotate provider environment values. For a provider credential rotation:

1. Verify the exact project, role, secret name and new enabled version. Read only that scoped Secret Manager payload and update only `temporal-worker-ROLE-runtime` through memory/stdin. Record nonsecret version metadata; leave the old provider credential usable through verification where supported.
2. Pause relevant admission and perform the reviewed worker drain. Environment values from `envFrom` do not change inside an existing process, and the Temporal mounted-key watchdog does not reload them. Preserve original execution/provider evidence and unresolved-mutation barriers during the drain.
3. Roll out the reviewed worker version/process under the existing deployment and capacity checks. Confirm old SDK instances have stopped, new Pods read the selected configuration, and actual readiness/routing and safely scoped functional verification pass.
4. Revoke/disable the old credential/version only after successful verification. Recover using the retained old version if the replacement fails. Do not introduce an additional secret controller or an unreviewed forced replay to rotate credentials.

## Truthful readiness and rollout

For the initial zero-activity `WorkerRestartProbe`, set `dispatcherEnabled:false` in the reviewed platform descriptor before rendering/deploying workers, and withhold publishing/image credentials. If the configured email role requires SMTP settings for startup, supply only its already-reviewed active kit mapping; this zero-activity probe sends no email or other provider activity. The generated Pod explicitly sets `TEMPORAL_DISPATCHER_ENABLED=false` before startup; a runtime Secret cannot override it. Worker readiness still requires the actual namespace connection, pollers and provenance, while `/healthz` reports `dispatcherEnabled:false`. This probe configuration is not eligible for application cutover. Before opening ownership, deploy the reviewed normal descriptor (`dispatcherEnabled:true`, or the unchanged normal default), verify live orchestration Pods explicitly contain `TEMPORAL_DISPATCHER_ENABLED=true`, and confirm the health field. The release gate rejects a disabled dispatcher even if its restart proof passes.

Initial worker deployment requires a fresh private, nonsecret `cloudEvidence` report: `schemaVersion:1`, `connectionMode:temporal-cloud`, exact `projectId`, `accountId:qwejt`, full `namespace`, `provider:gcp`, primary `region:us-central1`, exact `address`, actual `namespaceState:ACTIVE`, `replicaRegions:[]`, `highAvailabilityEnabled:false`, actual `tlsVerified`/`namespaceAccessVerified`, `runtimePermission:Write`, `runtimeServiceAccountScope` equal to the namespace, and `verifiedAt` within one day.

Cloud release preflight reads only the scoped Cloud connection report and original-run worker restart proof. It does not read a database backup, SQL schema, WAL restore, PITR or failover report. The selected single-VM mode explicitly rejects replica configuration; the self-hosted backup validator remains separate.

Cutover preflight additionally requires actual original-run restart/resume proof in `recovery`: `result:passed`, immutable `workerBuildId`, actual `clusterUid`, original `workflowId`/`runId`, `workerRestarted:true`, `resumedOriginalExecution:true`, and `sideEffectsDisabled:true`. This is a worker restart test, not a disaster-recovery or database restore claim.

`gce.mediaDiskGiB` records the actual raw provisioned disk size (470GiB in staging); `gce.mediaRequiredCapacityGiB:400` separately records the required usable filesystem capacity. Filesystem overhead must not be counted as usable space. `gce.mediaFilesystemEvidence` names a private actual mount report: `schemaVersion:1`, exact `projectId`/`instanceId`/`clusterUid`, `mountPoint:/var/lib/urm-temporal/media`, actual `device`, `filesystem:ext4`, actual `totalBytes` covering400Gi and `verifiedAt` within one day. Collect it from the mounted host filesystem; a desired disk size or an ordinary directory is insufficient.

Cloud emits worker/network/worker-metrics manifests only. No self-hosted server/schema/Postgres/certificate/PITR artifacts are rendered. Existing application failure injection, provider-reference backfill, legacy task drain, actor/generation fences, open staging E2E, human smoke acceptance and approval before main remain required. Firebase functions continue to receive only generated ownership/release flags from private release control, because they admit work through Firestore and have no Temporal API credentials. See [monitoring guidance](https://docs.temporal.io/cloud/monitor).

The old self-hosted mode and explicitly optional `*.gke-cloud.example.json` templates remain available. They are not prerequisites for this simple path or evidence of resources provisioned.

## Cost assumptions checked 2026-10-12

At Iowa on-demand list prices, e2-standard-4 costs $0.13402284/hour, about **$98/month per VM** at 730hours. Balanced boot/scratch disks, public IPv4, network and logs add costs; with approximately470–500GiB scratch, a practical preliminary allowance is approximately **$150–$180/month per environment**, or **$300–$360/month for both**. Actual disk/network usage and any temporary upgrade capacity determine the bill. No GKE control-plane fee or replicated infrastructure is included. [Compute prices](https://cloud.google.com/products/compute/pricing/general-purpose).

## Building the worker in Cloud Build

Use `ops/temporal/cloudbuild.worker.json` for a regional Linux amd64 build when a local Docker host lacks capacity. It explicitly enables BuildKit so `apps/temporal-worker/Dockerfile.dockerignore` controls the worker context; the legacy Docker builder instead applies the unrelated root context and omits required Functions sources. The image build checks Temporal protobuf identity and supported history conversion after production dependency pruning.

Submit a clean export of the reviewed commit, not a dirty checkout. Set `_BUILD_ID` to that exact full commit and `_IMAGE` to the environment's Artifact Registry repository plus the same commit tag. For staging, submit in `urm-app-staging`, region `us-central1`, with `--config ops/temporal/cloudbuild.worker.json`, `--substitutions _BUILD_ID=FULL_COMMIT,_IMAGE=FULL_IMAGE_TAG`, and `--ignore-file apps/temporal-worker/Dockerfile.dockerignore` resolved against the exported source. Cloud Build's build identity needs source access, log writing and repository-scoped image push access; it must not reuse the application's worker identity. After the build succeeds, use its actual `results.images[].digest` in the platform descriptor. Never infer a digest from the tag.

A worker-only upgrade on the single server may require stopping the previous idle version before starting the new one. Keep application admission and dispatch paused, prove no running workflows, wait for all previous Pods to terminate, then deploy/promote the new version. Retire the previous version only after Temporal's drainage and task-queue checks pass.
