# Controlled release and automatic backend deployments

Both staging/main selective workflows wrap every Firebase rules/indexes/function/kit mutation, retired-function deletion and Storage CORS update with `scripts/temporal-deploy-guard.mjs`. Pushes and full manual workflow dispatch use the same guard. Sentry release tracking does not deploy a backend and remains separate. Existing branch protection remains in force.

The guard authenticates with the workflow's existing Google OIDC ADC, after `setup-backend-deploy`. That identity must be able to read the default Firestore database and transactionally create/delete `_control/temporalReleaseOperation`, and read `_control/temporalRelease` / `_control/temporalReleaseState`. The normal project-scoped `roles/datastore.user` role includes these data-plane permissions; retain the deployment identity's already-reviewed Functions/Storage/rules permissions. Verify actual IAM bindings before the first run. Authentication or Firestore permission failures stop before any child deployment starts; this source change does not itself grant IAM access. Actual project IAM inspection confirmed the documented identities `github-staging-deployer@urm-app-staging.iam.gserviceaccount.com` and `github-production-deployer@urm-app.iam.gserviceaccount.com` already have `roles/firebase.admin`, whose reviewed definition includes the required datastore read/create/update/delete permissions. No new IAM grant is needed for those identities. GitHub secret email values are not readable through this inspection; the guard still authenticates and checks actual access at execution.

Acquisition reads checkpoint/control/operation lock in one Firestore transaction. An automatic mutation is refused throughout an active controlled release, including the interval after admission opens but before `restore-auto` marks the checkpoint complete. Parallel automatic mutation commands wait for the same nonexpiring lock, bounded to55 minutes, and recheck checkpoint state on every attempt. No lock is expired or stolen. A controller freeze uses the same lock: it refuses an already-running deployment; once frozen, subsequent automatic jobs cannot write. The unchanged immutable checkpoint binds source identity throughout cutover. A suppressed automatic deploy fails visibly; it is never recorded as a successful backend deployment.

The guard holds authority while the child command runs, and while Functions env files are materialized from current private control. It releases only its matching `operationId` after successful child completion. SIGINT/SIGTERM forward to the child process group; interruption, child failure, failed spawning, lost connection or process death leaves the lock for review. A process exit is not proof that previously submitted asynchronous Firebase operations stopped. Job cancellation or an old creation timestamp never authorizes deleting a lock.

## Explicit pinned deployment

From the actual checkout of the reviewed `compatibilityCommit`, after freezing and merging through the normal protected PR flow:

```sh
node scripts/temporal-deploy-guard.mjs \
  --project urm-app-staging --release /private/release.json --phase ui-frozen \
  --materialize-function-env -- bash /private/deploy-reviewed-backends.sh
```

The reviewed deployment script runs the project's required rules/indexes, all Functions codebases, standalone kits and independent runtime services from that checkout. Prepare kit configuration/dependencies before invoking the guard. Use the same wrapper with `--phase ownership-changed` for the deployment after ownership transfer. These deployments intentionally use different private ownership flags. Do not recursively invoke the guard from inside the already-guarded deployment script. Commands requiring several child deployments should remain in this one guarded script, with `set -euo pipefail`, so a failed mutation cannot be hidden by later successes.

Start from a clean committed checkout before installing/preparing deployment artifacts. Both the guard and function-env writer check tracked/staged source and nonignored untracked files against the pinned HEAD; pending source edits, staged changes and new untracked source block deployment. Four split `functions-*/package.json` files may differ only by the exact catalog resolution and JSON serialization derived from the pinned package manifests/workspace catalog; changes to scripts, other dependency versions or fields still fail. `functions/src/sentryBuildInfo.ts` may differ only by the exact generated one-line pinned SHA. The guard supplies `SENTRY_GIT_SHA` to its children. Existing ignored `firebase.legacy.json` / `firebase.kits.json` must equal the deterministic selections of pinned `firebase.json`, including the explicitly supported no-search selection. Private provider/env settings and ignored build artifacts remain operational inputs; normal deployment prebuild regenerates compiled application outputs. The guard repeats source checks after acquiring authority and after successful child completion; changed source leaves the lock for review. Tracked kit instance env files may differ only by the exact `upsertFunctionFlags` output from that pinned original file, current project's authoritative private control and pinned commit; provider settings cannot change through this exception. Other-project instance env and disabled staging search env receive no exception. Root `/gha-creds-*.json` files created by Google Actions auth are narrowly ignored and excluded from applicable Docker contexts; other untracked files remain blocked. Do not stage generated transformations or manually patch generated deployment configs.

Ownership transfer changes expected generated env flags. The previous compatibility output is not accepted as the new control's output. Before postownership preparation, inspect the tracked target-project instance env paths against their saved actual compatibility control and pinned baseline; verify they contain exactly the prior generated flags with unchanged provider settings. Then explicitly restore **only those reviewed tracked paths** from the pinned commit, for example `git restore --source FULL_PINNED_SHA --worktree -- PATH_A PATH_B`, and run the guarded `--phase ownership-changed --materialize-function-env` deployment. Obtain the paths from `firebaseEnvironmentSources` intersected with tracked files for that project; do not restore another project's env. This restoration is a deliberate operator step, not an automatic overwrite. Modified provider settings or unverified old flags require separate review. Isolated fixture tests cover legacy compatibility generation, rejection after current ownership changes, explicit pinned restoration, and successful Temporal regeneration/postdeployment verification on the same checkout.

Both explicit phases require the exact release UUID, mode, domain list, backend/UI commits, checkpoint phase, matching control revision and paused admission. The actual checkout SHA must equal the pinned compatibility commit. Normal automatic jobs likewise require their actual checkout to equal `GITHUB_SHA`; a genuine merge checkout may correctly use its own merge SHA after the controlled release completes. `temporal-function-env.mjs --commit` cannot stamp a different commit onto the current checkout. No merge-built backend may be relabelled as the PR-head source. For the initial merge, compare its source tree with the reviewed head and stop for review if they differ.

## Reconcile a retained failed operation

1. Stop queued automatic deployment runs for this project while inspecting. Read the exact project, operation ID, commit, creation timestamp and GitHub run/attempt from `_control/temporalReleaseOperation`. Inspect the matching run logs and any operator process; confirm the child process group is stopped. Do not print secret payloads or materialized env files.
2. Inspect the actual APIs involved in that command, using the operation/resource IDs from its logs: Cloud Functions v1/v2 long-running operations and target function states; Cloud Run revisions/services for Gen2 Functions or independent runtimes; Firebase Rules releases and Firestore index operations; and the exact Storage bucket's current CORS configuration. Follow every submitted operation to a terminal state. A lost CLI connection or cancelled GitHub run does not cancel a submitted server operation.
3. Record actual terminal results and the resulting deployed source/ownership configuration. If any operation remains pending or uncertain, retain the lock and wait/reconcile. If source, revision or ownership differs from the reviewed checkpoint, keep admission paused and correct the deployment through the controlled release before continuing.
4. Only after this inspection confirms settlement, use an authenticated operator transaction to read `_control/temporalReleaseOperation` again, compare the exact reviewed `operationId`, and delete that same document atomically. `releaseDeploymentLock(firestore, reviewedOperationId)` from the guard module implements the identity comparison; invoke it only after the preceding manual reconciliation. It refuses a changed or missing identity. Never delete by age, replace another owner's document, or add a failure-path cleanup trap.
5. Resume with the original immutable release descriptor and phase. Rerun actual backend verification; a cleared lock supplies no readiness evidence. Automatic deployment remains blocked until the controlled checkpoint is complete.
